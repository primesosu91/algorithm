# Competitive Programming 運用ガイド

## 1. 基本構成

競技プログラミングに関する作業は、原則として `Competitive Programming` Project内で行う。

Project内では、以下の役割を分けて管理する。

### Projectの「指示」

競技プログラミング全体に共通する最小限のルールを保存する。

デバッグ専用・ライブラリ開発専用など、特定用途だけの詳細な規約はここへ直接まとめない。

### ChatGPT Library

用途別の詳細な規約や、Project全体から参照したい資料を保存する。

現在の主要な規約：

* `DebugRules.md`
* `競技プログラミング ライブラリ開発規約.md`
* `Competitive Programming 運用ガイド.md`

ライブラリの最新版ソースと命名・APIカタログはGitHubへ直接参照する。全ソースをChatGPT LibraryやProjectへ個別に常設する必要はない。`UnionFind.cpp` だけを代表的なスタイルの参照用コピーとして常設してもよいが、使用前にGitHub版を確認する。

### GitHubの管理資料

対象リポジトリは [`primesosu91/algorithm`](https://github.com/primesosu91/algorithm) とする。

* `docs/NamingAndAPI.md`: 既存の完全な公開シグネチャ・意味・共通方針・例外を調べる中核資料。
* `docs/LibraryWorkflow.md`: 実践的な作業手順、Git操作、チャットの起動文。
* `docs/LibraryDevelopmentRules.md`、`docs/CompetitiveProgrammingGuide.md`、`docs/DebugRules.md`: ChatGPT Libraryにある規約本文の同内容の参照用写し。

規約本文の正式版はChatGPT Library、ソースとカタログの正式版はGitHubである。規約を改訂するときは参照用写しも同期し、不一致を放置しない。

### Project Rules チャット

Projectの規約を新規作成・修正するときに使用する。

通常の問題解決やライブラリ実装には使用しない。

### Library Development チャット

ライブラリ開発の運用方法や設計方針そのものについて相談するときに使用する。

個別ライブラリの実装作業には原則として使用しない。

---

## 2. デバッグするとき

原則として、1問題につき1つの新しいチャットを作成する。

チャットには可能な限り以下を提示する。

1. 問題文
2. 制約
3. 現在のコード
4. WA / TLE / RE / CEなどの結果

AtCoderのURLだけに依存せず、問題文・制約・コードを直接提示することを基本とする。

デバッグ時は、ChatGPT Libraryに保存されている `DebugRules.md` に従う。

問題のデバッグが終了したら、そのチャットを別問題に流用する必要はない。

---

## 3. 新しいライブラリを作るとき

原則として、1ライブラリにつき1つの新しいチャットを作成する。

チャット名はライブラリ名とする。

例：

```text
UnionFind
FenwickTree
SegmentTree
LCA
```

新規作成時は、最初に以下のように依頼する。

```text
○○ライブラリを新規作成したいです。
ChatGPT Libraryの「競技プログラミング ライブラリ開発規約」と「Competitive Programming 運用ガイド」に従って進めてください。
GitHub primesosu91/algorithm の最新版の docs/NamingAndAPI.md、data_structure/UnionFind.cpp、関連する既存ソースを確認してから設計してください。
GitHubの確認コミットと参照したファイルを明示し、既存APIを勝手に変更しないでください。
```

設計前にカタログと関連するGitHubの最新版ソースを読み、既存コードとの統一性確認に使用する。GitHubへアクセスできない場合に限り、必要なファイルだけを一時的に提示する。詳細な起動文は [`docs/LibraryWorkflow.md`](https://github.com/primesosu91/algorithm/blob/main/docs/LibraryWorkflow.md) を参照する。

---

## 4. 既存ライブラリを修正するとき

原則として、そのライブラリを作成した既存チャットを再利用する。

例：

`UnionFind` の修正 → 既存の `UnionFind` チャットを使用する。

ただし、大規模な再設計などで会話を分離した方が明確になる場合は、新しいチャットを作成してよい。

コードの正式な原本はGitHubである。

チャット履歴やChatGPT LibraryのコピーとGitHub版が異なる場合は、必ずGitHub版を正とする。

修正前に対象ソース、カタログ、`UnionFind.cpp`、関連するGitHubの最新版ソースを確認する。GitHubへアクセスできない場合は、対象版と未確認事項を明記し、必要なソースだけを提示してから修正を開始する。

---

## 5. ライブラリ作成後の流れ

新しいライブラリは、原則として以下の順番で運用する。

```text
新規作成
↓
基本・境界テスト
↓
必要に応じてランダムテスト・愚直比較
↓
検証中
↓
命名・APIカタログを作成／更新
↓
GitHubへ保存
↓
オンラインジャッジで実際に使用
↓
AC
↓
正式採用
```

テスト方法の詳細は「競技プログラミング ライブラリ開発規約」に従う。

ソースとカタログは原則として同じコミットで保存する。公開API変更時も同様に更新する。GitHubへの保存やカタログ収録だけでは正式採用にはならず、第9節のAC確認を必要とする。

---

## 6. GitHubの役割

GitHubをライブラリコードの正式な原本（Single Source of Truth）とする。

リポジトリ直下は、原則として以下のカテゴリで管理する。

```text
README.md
docs/
tools/
data_structure/
graph/
math/
string/
geometry/
algorithm/
utility/
```

必要なカテゴリのフォルダは、実際にライブラリを追加するときに作成すればよい。

`docs/` は管理資料、`tools/check_catalog.py` はソースの収録漏れ・カタログとの確認SHAのずれ・ローカルリンクを調べる補助スクリプトに使用する。ソース本体のカテゴリ別構成は維持する。

ライブラリは該当カテゴリに1ファイルずつ保存する。

例：

```text
data_structure/UnionFind.cpp
```

バージョン履歴はGit/GitHubのコミット履歴で管理し、コード本体に `v1.0` などの独自バージョン番号は付けない。

---

## 7. READMEの役割

GitHubのREADMEは、原則としてライブラリを探すための目次として使用する。

カテゴリ別にライブラリへのリンクを並べる。

例：

```text
Data Structure
- UnionFind
- FenwickTree
- SegmentTree

Graph
- Dijkstra
- SCC
- LCA
```

採用状態やAC履歴などの管理情報をREADMEに記載することは必須としない。

管理資料へのリンクは目次の補助として追加してよい。READMEへAPI仕様や規約全文を重複掲載しない。

---

## 8. ChatGPT Libraryの役割

ChatGPT Libraryには、Projectで使用する詳細な規約文書を保存する。全ライブラリのソースの個別アップロードは原則として行わない。

規約文書については、ChatGPT Libraryに保存されている最新版を正とする。

現在の主要な規約：

```text
DebugRules.md
競技プログラミング ライブラリ開発規約.md
Competitive Programming 運用ガイド.md
```

自作ライブラリのコード、`docs/NamingAndAPI.md`、`docs/LibraryWorkflow.md` はGitHubへの直接参照を基本とする。カタログ・手順書をアップロードしなくても、Projectの指示に固定したリンクから最新版を確認できる運用にする。

`UnionFind.cpp` は代表的なスタイルの参照用コピーとして常設してもよい。他のソースは作業時に必要なものだけを取得する。コピーを原本として扱わず、カタログやコピーとGitHubの実装が異なる場合はGitHubの最新版実装を正とする。

常設資料は原則として3規約と、任意の `UnionFind.cpp` だけでよい。命名資料の直接参照ができない環境では、カタログの確認コミットを付けた一時コピーを利用し、必要なソースとの照合を省略しない。

既存の参照用コピーは今回の移行で自動削除しない。GitHub側の保存とアクセスを確認した後、ユーザーが不要と判断したProject内の添付だけを任意に整理する。Libraryのファイルそのものの削除は別の明示的な指示がある場合に限る。

---

## 9. ライブラリの採用状態

新規ライブラリは、必要なテストを通過した段階では「検証中」とする。

対象ライブラリの検証に適したオンラインジャッジの問題で実際に使用し、ACした後に「正式採用」とする。

AtCoderに限定せず、Library Checkerなどを利用してよい。

正式採用の確認に使用した最初のAC問題を1件記録する。

AC記録はライブラリ本体には含めず、ユーザーが別途管理する。

正式採用後に動作へ影響する変更を加えた場合の扱いは、「競技プログラミング ライブラリ開発規約」に従う。

---

## 10. 規約を変更するとき

実際の運用中に問題や不足が見つかった場合のみ、必要に応じて規約を変更する。

将来起こる可能性だけを理由に、過度に規約を増やさない。

規約を変更するときは `Project Rules` チャットを使用する。

変更時は、

1. 変更する内容を確認する
2. 既存規約の必要箇所だけを修正する
3. 修正版全文を確認する
4. 修正版でChatGPT Libraryの同じ規約ファイルを更新し、ファイルの同一性と版履歴を維持する
5. GitHubの規約の参照用写しを同内容へ同期し、カタログ・手順書との矛盾を確認する

という順番を基本とする。

同じ規約の旧版と新版をChatGPT Libraryへ同時に残し続けない。

同じファイルの版履歴を使い、新版を別ファイルとして増やさないことを基本とする。過去に別ファイルの旧版がある場合でも、確認なしに削除せず、ユーザーの明示的な指示に従う。直接更新できない場合は修正版全文と差し替える対象名・手順を提示する。

---

## 11. チャットの使い分け

基本方針は以下とする。

* 新しい競プロ問題のデバッグ → 新しいチャット
* 新しいライブラリ → 新しいチャット
* 既存ライブラリの修正 → 原則として既存のライブラリチャット
* ライブラリ運用の相談 → `Library Development`
* 規約の作成・変更 → `Project Rules`

通常作業のたびに運用方法を最初から確認する必要はない。

実際に困ったことや既存ルールでは判断できないことが発生した場合に、運用方法や規約を見直す。

具体的な日常作業と再利用できる起動文は [`docs/LibraryWorkflow.md`](https://github.com/primesosu91/algorithm/blob/main/docs/LibraryWorkflow.md) にまとめる。手順書は規約の重複を避け、本ガイドと開発規約を参照する。
