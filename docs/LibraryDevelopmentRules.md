# 競技プログラミング ライブラリ開発規約

## 1. 基本方針

- 競技プログラミングで実戦使用する自作ライブラリを作成する。
- 実用性、短さ、使いやすさ、覚えやすさ、バグの入りにくさを優先する。
- 汎用性や設計の美しさは、実戦上の明確な利点がある場合に取り入れる。
- 過度な抽象化やオーバーエンジニアリングを避ける。
- AtCoder Library（ACL）には原則として依存しない。
- ライブラリは必要最小限のAPIから始め、実際に必要になった機能を追加する。
- マクロには依存しない。

## 2. 構造

- 原則として `struct` を中心に実装する。
- 状態を持つ必要がない処理など、`struct` にする必要がない場合は通常の関数を使用してよい。
- `class` は特別な理由がない限り使用しない。
- メンバは基本的に `public` とする。
- 本当に内部実装専用の補助関数などに限り、必要に応じて `private:` を使用する。
- 不必要なカプセル化は行わない。

## 3. 命名規則

### ライブラリ・struct名

PascalCaseを使用する。

略語として定着している名前は大文字を使用する。

例：

```cpp
struct DSU;
struct LCA;
struct SCC;
struct FenwickTree;
struct SegmentTree;
```

### 関数・変数

以下は `snake_case` を使用する。

- メンバ関数
- メンバ変数
- 通常の関数
- ローカル変数

例：

```cpp
range_sum(left, right);
component_size(v);
```

具体的な操作名・引数順序・返り値は、GitHubの [`docs/NamingAndAPI.md`](https://github.com/primesosu91/algorithm/blob/main/docs/NamingAndAPI.md) と関連する既存ソースコードを設計前に確認する。

同じ意味の操作は既存の名前を優先する。ただし、アルゴリズム固有の慣習や意味の違いによる合理的な例外は維持し、理由をカタログに記録する。既存APIの事後的な改名は行わない。

## 4. 型

型は役割に応じて使い分ける。

### 原則 `int`

- 配列の添字
- 頂点番号
- サイズ
- 個数など、構造を表す整数

### 必要に応じて `long long`

- 値
- 和
- 距離
- コスト
- 重み
- オーバーフローの可能性がある計算

格納する値の型を固定する必然性がないライブラリでは、実用上有益な場合にテンプレート化する。

テンプレート構文は、

```cpp
template<class T>
```

を使用する。

外部で定義された `ll` などの型エイリアスには依存せず、必要な場合はライブラリ内部で `long long` と明記する。

## 5. 添字と区間

- 公開APIは原則として0-indexedに統一する。
- 内部実装では、Fenwick Treeなどアルゴリズム上自然な場合に1-indexedを使用してよい。
- 区間を扱う公開APIは原則として半開区間 `[left, right)` に統一する。

## 6. 初期化

- 必要なサイズや設定値は原則としてコンストラクタで受け取る。
- コンストラクタ実行後、すぐ使用可能な状態にする。

例：

```cpp
DSU dsu(n);
FenwickTree<long long> fw(n);
```

- `init()` は再初期化など明確な利点がある場合にのみ追加する。

## 7. 前提条件の確認

- 競技プログラミング用途として軽量な設計を優先する。
- APIの前提条件確認には必要に応じて `assert` を使用する。
- 重い入力検証や例外中心の設計は原則として行わない。

## 8. コメント

コメントは、コンテスト中にコードを見直したとき、APIや実装の意図を素早く理解できる量を付ける。

### 公開関数

各公開関数の直前に、引数の順番・意味・返り値などがすぐ分かる短いコメントを書く。

例：

```cpp
// 更新: add(位置, 加算する値)
void add(int pos, T value);

// 区間和: range_sum(左端, 右端) -> [left, right)
T range_sum(int left, int right);

// 判定: same(頂点u, 頂点v) -> 同じ連結成分なら true
bool same(int u, int v);
```

必要に応じて以下も記載する。

- 返り値の意味
- 対象区間
- 計算量
- 特殊な前提条件

### 実装内部

- 意味のある処理ブロックごとに簡潔なコメントを付ける。
- コードをそのまま日本語にしただけの逐語的コメントは避ける。
- コメント量を減らしすぎず、実戦中に読み返しやすい状態を維持する。

## 9. ファイル

- 1ライブラリ = 1ファイルを原則とする。
- ライブラリは他の自作テンプレートに依存せず、可能な限り単独で利用できるようにする。
- 各ライブラリの先頭は原則として以下とする。

```cpp
#include <bits/stdc++.h>
using namespace std;
```

- `rep`、`all`、`chmin` など外部マクロに依存しない。
- 外部の型エイリアスにも依存しない。
- 保存するライブラリ本体にはテスト用 `main()` を含めない。
- テストが必要な場合は、ライブラリ本体とは別にテスト用 `main()` またはテストファイルを用意する。

## 10. API設計

- 最初から大量の機能を実装しない。
- 実戦で頻繁に必要となる最小限のAPIから開始する。
- 新しい機能は、実際の問題で必要になった場合など、追加する理由が明確なときに追加する。
- 既存APIは原則として維持する。
- 関数名、引数順序、返り値の意味などを安易に変更しない。

破壊的変更が必要な場合は、変更前に以下を説明する。

1. 変更が必要な理由
2. 影響を受けるAPI
3. 移行方法

ユーザーの了承を得てから破壊的変更を行う。

## 11. テスト

ライブラリを使用可能と判断する前に、そのアルゴリズムに適した検証を行う。

基本的に確認する項目：

- 基本ケース
- 境界ケース
- `N = 1`
- 空区間 `[x, x)`（該当する場合）
- 最初・最後の位置
- 値の極端なケース
- オーバーフロー
- 添字範囲
- 計算量

適切な場合はさらに、

- ランダムテスト
- 愚直実装との比較

を行う。

すべてのライブラリに機械的に同じテストを適用するのではなく、そのアルゴリズム固有の壊れやすいケースを考えて検証する。

## 12. ライブラリ作成時の回答

新しいライブラリを作成するときは、原則として以下を提示する。

1. ライブラリ本体
2. 使い方
3. 最小使用例
4. 計算量
5. 実施したテストと結果

最小使用例は、保存するライブラリ本体とは分離する。

## 13. 採用状態

ライブラリには概念上、以下の2状態を設ける。

### 検証中

実装後、そのライブラリに適した基本・境界・ランダム・愚直比較などの検証を通過した状態。

### 正式採用

以下を両方満たした状態。

1. 必要な検証を通過している。
2. 実際のオンラインジャッジの問題で使用し、1回以上ACしている。

AtCoderに限定せず、Library Checkerなど、対象ライブラリの実装検証に適したオンラインジャッジを利用してよい。

正式採用を確認するため、最初にACした問題を1件記録する。

この使用履歴はライブラリ本体には書かず、ユーザーが別途管理する。

正式採用済みライブラリに動作へ影響する変更を加えた場合は、状態を再び「検証中」に戻す。

その後、

- 必要な再テスト
- オンラインジャッジでの再度のAC確認

を経て正式採用へ戻す。

コメントや空白など、動作に影響しない変更だけの場合は正式採用状態を維持してよい。

## 14. 保存と原本

ライブラリの唯一の正式なソースコードの原本（Single Source of Truth）はGitHubの [`primesosu91/algorithm`](https://github.com/primesosu91/algorithm) とする。

全ライブラリをChatGPTへ個別アップロードし、参照用コピーを常設する運用は原則として廃止する。命名・APIカタログと関連するGitHubの最新版ソースを直接参照する。

`UnionFind.cpp` は代表的な設計・記述スタイルの基準とする。ChatGPT側に常設する場合も参照用コピーであり、設計・修正前にはGitHub版との一致を確認する。

GitHubの最新版とカタログ、チャット履歴、ChatGPT側のコピーに差異がある場合は、必ずGitHubの最新版ソースを正とする。確認できない情報を記憶から補完しない。アクセスできない場合は未確認事項を明示し、該当作業に必要なファイルだけを一時的に提示してもらう。

GitHubのREADMEは原則として、カテゴリ別にライブラリへのリンクを並べる目次として使用する。

採用状態やAC履歴などの管理情報をREADMEに記載することは必須としない。

## 15. バージョン管理

- バージョン履歴はGit/GitHubのコミット履歴で管理する。
- ライブラリコード自体に `v1.0`、`v1.1` などの独自バージョン番号は付けない。
- 変更履歴を確認する必要がある場合はGitの履歴を利用する。

## 16. 既存ライブラリとの統一

新しいライブラリを作成・既存ライブラリを修正するとき、設計前にGitHubの `docs/NamingAndAPI.md`、最新の `data_structure/UnionFind.cpp`、対象と関連する既存ソースコードを確認し、それらとの統一性を確認する。カタログだけで実装の確認を代替しない。

特に以下を確認する。

- 命名
- API設計
- コメント形式
- 型の使い方
- 添字
- 区間表現
- 初期化方法
- コーディングスタイル

ただし、既存ライブラリに問題がある場合は無条件に踏襲せず、その問題を明示して改善案を提示する。

新規ライブラリの完成後、および既存の公開API・前提条件・返り値の意味が変わった後は、`docs/NamingAndAPI.md` の一覧、該当API、例外、確認したソースのblob SHAを更新する。原則としてソースとカタログを同じコミットで同期する。コメント・空白だけの変更でも、内容を照合して確認SHAを更新する。

既存APIの破壊的変更には第10節の説明とユーザーの明示的な了承が必要である。カタログ整備だけを理由に既存コード・公開APIを変更しない。

- 詳細な規約本文はChatGPT Libraryの最新版を正とする。GitHubの `docs/LibraryDevelopmentRules.md`、`docs/CompetitiveProgrammingGuide.md`、`docs/DebugRules.md` は同内容の参照用写しとし、規約改訂時に同期する。
- 命名・API参照の中核資料はGitHubの `docs/NamingAndAPI.md` とする。ソースとの不一致は最新版ソースを確認してカタログを修正する。
- 実際の作業順、Gitコマンド、再利用できる起動文は [`docs/LibraryWorkflow.md`](https://github.com/primesosu91/algorithm/blob/main/docs/LibraryWorkflow.md) を参照する。手順書は本規約・運用ガイドの要求を変更しない。
