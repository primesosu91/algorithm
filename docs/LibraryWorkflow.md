# LibraryWorkflow — 自作ライブラリの実践的な運用手順

対象: [primesosu91/algorithm](https://github.com/primesosu91/algorithm)、C++23。1ライブラリにつき1チャットを基本とする。読み返した際はまず以下の資料とGitHubの最新版を確認する。

| 判断すること | 参照先 |
| --- | --- |
| 実装・設計・テスト・採用・破壊的変更の要件 | ChatGPT Libraryの `競技プログラミング ライブラリ開発規約.md`（[GitHubの同内容の写し](LibraryDevelopmentRules.md)） |
| Project・チャット・資料の役割 | ChatGPT Libraryの `Competitive Programming 運用ガイド.md`（[GitHubの同内容の写し](CompetitiveProgrammingGuide.md)） |
| デバッグの進め方・修正回答 | ChatGPT Libraryの `DebugRules.md`（[GitHubの同内容の写し](DebugRules.md)） |
| 現在の名前・シグネチャ・共通点・例外 | [NamingAndAPI.md](NamingAndAPI.md) と各カテゴリの最新ソース |
| 代表的な型・コメント・書式 | [data_structure/UnionFind.cpp](../data_structure/UnionFind.cpp) |

規約本文はLibraryの最新版、ソースとカタログはGitHubを正式版とする。規約のGitHub写しは同期用であり、別の独立した規約ではない。本書は実行手順であって規約を変更しない。矛盾・版のずれがあれば作業開始時に明示して同期する。

## 1. 新しいチャット・作業を開始する

1. `Competitive Programming` Project内で、原則としてライブラリ名の新規チャットを作る。既存ライブラリ修正なら原則として元のチャットを使う。長い履歴・大規模な再設計では新しいチャットでもよい。
2. 第9節の起動文を貼り、目的・必要操作・入力条件を追加する。前のチャットの記憶だけを現在の仕様の根拠にしない。
3. ChatGPTはLibraryの規約を読み、GitHubの最新mainのコミットSHAを取得する。そのSHAに固定してカタログ、UnionFind、関連ソース、修正対象を読む。
4. カタログ項目の確認blob SHAと実装を照合する。違う場合は実装を先に読み、ずれを記録して更新する。GitHubにアクセスできなければ、未確認ファイルと必要な対象版を明記し、必要なものだけ一時提示してもらう。
5. 作業開始時に「対象リポジトリ・ブランチ・確認コミット・読んだファイル・今回変更する範囲」を短く記録する。

全ライブラリを毎回アップロードする必要はない。通常はカタログと関連する少数の実装を取得する。全体調査・規約改訂のときのみ全ソースを横断確認する。

### 手元のGit作業を始める場合

VS Codeで既存の `algorithm` リポジトリのフォルダを開き、そのフォルダのターミナルで実行する。保存場所は環境により異なるため、未知のパスへ移動・新規cloneする前に確認する。

```bash
pwd
git rev-parse --show-toplevel
git remote -v
git branch --show-current
git status --short
```

正常時はトップディレクトリが意図したリポジトリ、originが `primesosu91/algorithm`、通常のブランチが `main` と確認できる。`git status --short` は何も表示しなければ作業ツリーが空。変更があれば内容を確認し、未保存作業を消すコマンドは使わない。

作業ツリーが空で `main` の場合、最新版を取得する。

```bash
git fetch origin
git pull --ff-only origin main
git log -1 --oneline
```

成功すれば更新の表示または `Already up to date.` が出る。分岐して fast-forward できない・別ブランチ・ローカル変更がある場合は、エラーと状況をチャットへ提示する。`reset --hard`、強制push、勝手な履歴削除で解消しない。WorkがGitHubへ直接コミットした後も、この手順で手元へ取り込む。

## 2. 新しいライブラリを作成する

1. 必要な操作・用途・制約を整理する。不明な仕様は断定せず、条件を確認する。
2. カタログの「新規設計前の確認手順」から参照先を選び、UnionFindと近い実装を読む。
3. 最小限の公開API案を、完全なシグネチャ、引数の順序・型・意味、返り値、添字・区間、状態変更、前提、構築順で提示する。既存との共通点・合理的な違いを明記し、設計を合意する。
4. 該当カテゴリに1ファイルとして実装する。外部マクロ・自作テンプレート・ACLへの依存を避け、テストmainは別ファイルにする。
5. 第4節の検証を行う。検証後は「検証中」であり、GitHub保存・カタログ収録だけでは「正式採用」にしない。
6. カタログに全API・公開変数・前提・例外・確認blob SHAを追記する。新しいカテゴリは実際に必要な場合だけ作る。
7. 第5節の手順でソース・カタログ・必要ならREADMEを同じコミットへまとめる。
8. 適切なオンラインジャッジで使用してACし、最初のAC問題1件をユーザーの管理先へ記録する。証拠が揃ってから正式採用とする。

## 3. 既存ライブラリを修正する／命名に迷う

1. 最新の対象ソースとカタログを読む。問題修正ならDebugRulesも適用し、原因・反例を先に整理する。
2. 変更が必要な箇所を絞り、元のアルゴリズム・名前・コメント・書式を可能な限り維持する。
3. 名前に迷ったらカタログを概念で検索する。たとえば区間集約はprod、頂点列復元はget_path、集合挿入はinsertを起点に、引数と意味まで照合する。
4. 同じ名前の別の意味に注意する。`size/count` の対象、`capacity` の元容量／残余容量、`cost` の単位費用／総費用、`has_negative_cycle` の判定範囲等を確認する。
5. 同じ意味の既存APIを優先するが、アルゴリズムの慣習・対象・生成方式が違うなら、合理的な理由を残して違いを維持する。カタログの統一のために既存の名前を勝手に変えない。
6. 破壊的変更は理由・対象API・移行方法を具体化し、ユーザーの明示的な了承を得てから行う。これは開発規約第10節の要件である。すでに当該変更を具体的に了承されていれば、同じ了承を再度求めない。
7. 動作へ影響する変更では状態を「検証中」に戻し、必要な再テストと再AC後に正式採用へ戻す。コメント・空白だけなら採用状態を維持する。
8. 公開API・意味・前提が変わったらカタログを更新する。内部だけの変更でもソース確認SHAのずれを残さず、APIへの影響がないことを読んで確認する。

## 4. テスト・AC確認・正式採用

テスト要件は開発規約第11・13節を参照する。次は実行時に記録する順序である。

1. C++23でテスト用コードをコンパイルする。手元で使っているコンパイラの `-std=c++23` を指定する。必要ならデバッグ実行でAddress/UndefinedBehavior Sanitizerも使う。
2. そのアルゴリズムに適した基本・境界ケースを確認する。空区間・単一要素・端点・未到達・同一点・重複辺等は該当するときだけ含める。
3. 必要なら小さい入力の愚直比較・ランダム比較を行う。入力範囲、ケース数、seed、期待値、結果を記録する。最大制約の計算量・メモリ・数値範囲も確認する。
4. 自動テストが通過した段階では「検証中」と記録する。
5. 対応するオンラインジャッジの問題で、GitHubへ保存する実装と同じ版を使用してACを確認する。問題名・URL・提出IDまたは提出URL・ソースの対応コミットを記録できる範囲で残す。基本要件は最初のAC問題1件の記録である。
6. 必要な検証と実際のACが揃ったら正式採用とする。状態・AC履歴をソース本体へ埋め込まない。記録先は従来のユーザーの管理先を維持し、未確認ならチャットに記録文を提示して保存先を確認する。

カタログ確認スクリプトのOKは、アルゴリズムの正しさ・テスト通過・AC・採用の証拠ではない。既存の採用記録が現行コミットに対応するか不明なら「未確認」と記す。

## 5. GitHubへコミットする

実際のリポジトリのトップディレクトリで実行する。ここで `graph/NewLibrary.cpp` は例示のパスであり、実際に変更したファイル名に置き換える。

まず変更を確認する。

```bash
git status --short
git diff --stat
git diff
python3 tools/check_catalog.py
```

確認スクリプトの正常時は `OK: coverage, source fingerprints, and relative file links agree.`、終了コード0。失敗時は対象ファイルを表示する。ソース変更が表示されたら第6節に従って内容を照合する。

意図したファイルだけを指定して追加する。READMEを変えていなければREADMEの行は不要。

```bash
git add graph/NewLibrary.cpp docs/NamingAndAPI.md
git add README.md
git diff --cached --stat
git diff --cached
```

無関係な変更が含まれていないことを確認してからコミット・pushする。

```bash
git commit -m "Add NewLibrary and document its API"
git push origin main
git status --short
git log -1 --oneline
```

正常時はコミットSHAと変更ファイル数が出て、pushが成功する。最後のstatusが空なら手元に未コミット変更はない。pushが拒否されたら最新のリモートを確認して差分を統合し、強制pushはしない。main以外で作業している場合は、そのブランチをpushし、既存のレビュー手順に従う。

Workが接続済みGitHubへ直接反映する場合も、最新head確認・差分確認・ソースとカタログの同期を行う。基準headが変わっていたら最新版を再確認し、他の変更を上書きしない。反映後はコミットURL・変更ファイル・確認結果を報告する。

## 6. NamingAndAPI.mdを更新する

1. 新規追加なら全対象一覧のリンク・型名を追加し、該当カテゴリに項目を作る。更新なら既存項目を編集する。
2. ソースに明示した全公開型・通常関数・コンストラクタ・演算子・friend関数・公開変数を確認する。privateは公開APIとして記載しない。publicの内部補助は内部用と注記する。
3. 既定引数・テンプレート・戻り型・const・参照・削除された操作を含む完全なシグネチャを記録し、本体から動作と前提を確認する。コメントだけが古い場合も実装を正とする。
4. 添字・区間・引数順序・初期状態・呼出し順・未該当値・列の向きと長さ・値／参照を確認する。
5. 共通方針・例外の表に新しい情報がある場合だけ追記する。採用状態をカタログ収録から推定しない。
6. ソースを保存した後、実際のパスでblob SHAを取得する。

```bash
git hash-object graph/NewLibrary.cpp
```

表示された40桁をその項目直下の1行コメントへ書く。これは**ファイルのblob SHA**であり、コミットSHAとは異なる。

```text
<!-- catalog-source: graph/NewLibrary.cpp 表示された40桁のblob_SHA -->
```

部分更新時は、確認したコミットSHAも該当項目へ追記する。初回全体調査のコミットを、全ファイルを再確認せずに新しい全体基準へ置換しない。未コミットの新規ソースは「今回のコミットへ同時追加するソース」と明記し、blob SHAで実装を特定できる。

7. `python3 tools/check_catalog.py` を実行し、第5節のdiff確認で関数の意味・例外もレビューする。SHAだけ直して調査済みにしない。
8. ソースとカタログを原則同じコミットへまとめる。ライブラリが削除・移動された場合はユーザーの承認済み範囲に限りリンクと一覧も更新する。

スクリプトは標準Pythonのみを使い、リポジトリ内の `.cpp` と `catalog-source` を照合する。`tests/test/tools/build/.git` 配下のテスト・補助・生成物は対象外。API本文の自動生成、C++構文解析、リンクの外部HTTP検査、見出しアンカーの検査は行わない。規約改訂で収録対象を変える場合はスクリプトも同じ範囲へ調整する。

## 7. 規約そのものを改訂する

1. 原則として `Project Rules` チャットを使い、現行規約全文と具体的な問題を確認する。今回のようにユーザーが一括改訂を明示した作業では、その依頼チャットで進めてよい。
2. 必要な箇所だけ修正する。規約の既存要件、テストと採用の条件、破壊的変更の扱いを失わない。
3. 修正版全文・差分・変更理由を確認する。運用ガイド・カタログ・本書との矛盾も調べる。
4. Libraryの既存の同じ規約ファイルを更新し、ファイルの同一性・版履歴を維持する。新版を別名のファイルとして増やさない。
5. GitHubの対応する写しを同内容に同期する。`DebugRules.md` はデバッグ規約へ直接影響する場合だけ改訂する。
6. 片側しか更新できなかったら、成功した側・失敗した側・未同期の規約を明記する。完全な修正版を提示し、次項の差し替え手順を使う。規約の更新を「両側完了」と報告しない。

### WorkからLibraryを直接更新できない場合

1. 提示された完全な修正版を保存し、対象が「開発規約」か「運用ガイド」かを確認する。
2. ChatGPTのLibraryで `Competitive Programming` フォルダを開き、同名の現行ファイルを選ぶ。
3. ファイル更新・差し替え機能が表示されるなら、同じファイルを修正版へ更新する。表示名は環境により異なるので、実際にある項目を使う。
4. 直接差し替え機能がなければ、修正版をアップロードし、全文と名前が正しいことを確認してから、Projectの参照先を新版へ変更する。
5. 別ファイルの旧版が残った場合は、自分で不要と確認した対象だけを整理する。ソース・AC記録・無関係な資料をまとめて削除しない。Workは明示的な指示なしに旧資料を削除しない。

## 8. ChatGPT側の常設資料と今回の移行作業

| 保存・参照場所 | 常設する内容 | 増加への対応 |
| --- | --- | --- |
| Projectの指示 | C++23等の共通ルール、規約名、GitHubとカタログの固定URL | 全API・全ソースは貼らない |
| ChatGPT Library | 開発規約、運用ガイド、DebugRules | 既存ファイルを更新し、規約数を増やさない |
| Projectに任意添付 | UnionFind.cpp のスタイル参照コピー | 最新版はGitHubで照合。添付なしでも直接参照可 |
| GitHub | 全カテゴリのソース、NamingAndAPI、LibraryWorkflow、規約の写し、確認スクリプト | 新規ライブラリはソースとカタログだけ追加・更新 |
| 各ライブラリのチャット | 設計理由、作業履歴、テスト・AC報告、未解決事項 | 最新仕様をチャットの記憶だけで再構成しない |

今回の移行後、ユーザーが手動で行う順序は次のとおり。

1. 第10節の指示全文へProjectの指示を更新する。Projectを開き、現在の指示を編集する項目から貼り替え、保存する。画面の項目名が異なる場合は表示されている編集操作を使う。
2. 納品時の反映結果を確認する。Libraryの開発規約・運用ガイドが直接更新済みなら、再アップロードは不要。更新できなかったものだけ第7節に従って差し替える。
3. GitHubのカタログ・ソースへ実際にアクセスできることを確認する。新規チャットに第9節の起動文を貼り、基準コミット・参照ファイルを回答できるか確認する。
4. 手元のGitリポジトリへ第1節のfetch/pull手順で更新を取り込み、`python3 tools/check_catalog.py` を実行する。
5. 以上が確認できてから、不要と判断したライブラリの**Projectへの参照添付**を任意に外す。3規約と、常設するならUnionFindは維持する。カタログ・手順書は指示のURLから参照するため、添付は不要。
6. 参照添付を外す操作とLibraryファイル自体の削除は別として扱う。既存ファイルの一括削除は必要ない。明示的に削除したい場合だけ、対象・GitHub保存・AC記録を確認して別途実施する。

ファイルアップロード数に依存せず、固定URLから最新版を取得することが要点である。ChatGPTがURLの内容を常に自動取得できるとは保証しないため、起動時の確認コミット・参照ファイルの明示を省略しない。
