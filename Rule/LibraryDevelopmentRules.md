# 競技プログラミング ライブラリ開発規約

## 1. 基本方針

- 競技プログラミングで実戦使用する自作ライブラリを作成する。
- 実用性、短さ、使いやすさ、覚えやすさ、バグの入りにくさを優先する。
- 汎用性や設計の美しさは、実戦上の明確な利点がある場合に取り入れる。
- 過度な抽象化やオーバーエンジニアリングを避ける。
- AtCoder Library（ACL）には原則として依存しない。
- ライブラリは必要最小限のAPIから始め、実際に必要になった機能を追加する。
- マクロには依存しない。

## 2. 構造

- 原則として `struct` を中心に実装する。
- 状態を持つ必要がない処理など、`struct` にする必要がない場合は通常の関数を使用してよい。
- `class` は特別な理由がない限り使用しない。
- メンバは基本的に `public` とする。
- 本当に内部実装専用の補助関数などに限り、必要に応じて `private:` を使用する。
- 不必要なカプセル化は行わない。

## 3. 命名規則

### ライブラリ・struct名

PascalCaseを使用する。

略語として定着している名前は大文字を使用する。

例：

```cpp
struct UnionFind;
struct LCA;
struct SCC;
struct FenwickTree;
struct SegmentTree;
```

### 関数・変数

以下は `snake_case` を使用する。

- メンバ関数
- メンバ変数
- 通常の関数
- ローカル変数

例：

```cpp
range_sum(left, right);
component_size(v);
```

具体的な操作名・引数順序・返り値は、GitHubの [`Rule/NamingAndAPI.md`](https://github.com/primesosu91/algorithm/blob/main/Rule/NamingAndAPI.md) と関連する既存ソースコードを設計前に確認する。

同じ意味の操作は既存の名前を優先する。ただし、アルゴリズム固有の慣習や意味の違いによる合理的な例外は維持し、理由をカタログに記録する。既存APIの事後的な改名は行わない。

## 4. 型

型は役割に応じて使い分ける。

### 原則 `int`

- 配列の添字
- 頂点番号
- サイズ
- 個数など、構造を表す整数

### 必要に応じて `long long`

- 値
- 和
- 距離
- コスト
- 重み
- オーバーフローの可能性がある計算

格納する値の型を固定する必然性がないライブラリでは、実用上有益な場合にテンプレート化する。

テンプレート構文は、

```cpp
template<class T>
```

を使用する。

外部で定義された `ll` などの型エイリアスには依存せず、必要な場合はライブラリ内部で `long long` と明記する。

## 5. 添字と区間

- 公開APIは原則として0-indexedに統一する。
- 内部実装では、Fenwick Treeなどアルゴリズム上自然な場合に1-indexedを使用してよい。
- 区間を扱う公開APIは原則として半開区間 `[left, right)` に統一する。

## 6. 初期化

- 必要なサイズや設定値は原則としてコンストラクタで受け取る。
- コンストラクタ実行後、すぐ使用可能な状態にする。

例：

```cpp
UnionFind uf(n);
FenwickTree<long long> fw(n);
```

- `init()` は再初期化など明確な利点がある場合にのみ追加する。

## 7. 前提条件の確認

- 競技プログラミング用途として軽量な設計を優先する。
- APIの前提条件確認には必要に応じて `assert` を使用する。
- 重い入力検証や例外中心の設計は原則として行わない。

## 8. コメント

コメントは、コンテスト中にコードを見直したとき、APIや実装の意図を素早く理解できる量を付ける。

### 公開関数

各公開関数の直前に、引数の順番・意味・返り値などがすぐ分かる短いコメントを書く。

例：

```cpp
// 更新: add(位置, 加算する値)
void add(int pos, T value);

// 区間和: range_sum(左端, 右端) -> [left, right)
T range_sum(int left, int right);

// 判定: same(頂点u, 頂点v) -> 同じ連結成分なら true
bool same(int u, int v);
```

必要に応じて以下も記載する。

- 返り値の意味
- 対象区間
- 計算量
- 特殊な前提条件

### 実装内部

- 意味のある処理ブロックごとに簡潔なコメントを付ける。
- コードをそのまま日本語にしただけの逐語的コメントは避ける。
- コメント量を減らしすぎず、実戦中に読み返しやすい状態を維持する。

## 9. ファイル

- 1ライブラリ = 1ファイルを原則とする。
- ライブラリは他の自作テンプレートに依存せず、可能な限り単独で利用できるようにする。
- 各ライブラリの先頭は原則として以下とする。

```cpp
#include <bits/stdc++.h>
using namespace std;
```

- `rep`、`all`、`chmin` など外部マクロに依存しない。
- 外部の型エイリアスにも依存しない。
- 保存するライブラリ本体にはテスト用 `main()` を含めない。
- テストが必要な場合は、ライブラリ本体とは別にテスト用 `main()` またはテストファイルを用意する。

## 10. API設計

- 最初から大量の機能を実装しない。
- 実戦で頻繁に必要となる最小限のAPIから開始する。
- 新しい機能は、実際の問題で必要になった場合など、追加する理由が明確なときに追加する。
- 既存APIは原則として維持する。
- 関数名、引数順序、返り値の意味などを安易に変更しない。

破壊的変更が必要な場合は、変更前に以下を説明する。

1. 変更が必要な理由
2. 影響を受けるAPI
3. 移行方法

ユーザーの了承を得てから破壊的変更を行う。

## 11. テスト

ライブラリを使用可能と判断する前に、そのアルゴリズムに適した検証を行う。

基本的に確認する項目：

- 基本ケース
- 境界ケース
- `N = 1`
- 空区間 `[x, x)`（該当する場合）
- 最初・最後の位置
- 値の極端なケース
- オーバーフロー
- 添字範囲
- 計算量

適切な場合はさらに、

- ランダムテスト
- 愚直実装との比較

を行う。

すべてのライブラリに機械的に同じテストを適用するのではなく、そのアルゴリズム固有の壊れやすいケースを考えて検証する。

## 12. ライブラリ作成時の回答

新しいライブラリを作成するときは、原則として以下を提示する。

1. ライブラリ本体
2. 使い方
3. 最小使用例
4. 計算量
5. 実施したテストと結果

最小使用例は、保存するライブラリ本体とは分離する。

## 13. 開発の完了条件

オンラインジャッジへの提出・AC・再ACを開発の必須工程から外し、「検証中／正式採用」の個別管理は行わない。

承認した範囲の新規作成・修正は、以下を確認して完了とする。

1. C++23で第11節の対象固有の検証とリポジトリの共通チェックを通過している。構文確認だけで動作検証を代替しない。
2. ソース、スニペット、APIカタログ、必要なテスト・管理資料・作業記録が同期している。
3. 関連する変更をコミットし、GitHubのmainへ反映したことを確認している。ブランチ・PRまでの保存ならmain未反映と報告する。
4. 当該コミットのGitHub Actionsを取得できる場合は結果を確認する。実行中・失敗・取得不能の場合は、その状態と残る確認を明示し、成功したと報告しない。

動作へ影響する変更後は、必要な回帰テストと変更内容に応じた再検証を行う。コメント・空白だけの変更でも、ソース・カタログ・スニペットの整合性を確認する。

変更理由、対象ソース版、実施したテスト・入力範囲・結果、未確認事項は [DevelopmentLog.md](../records/DevelopmentLog.md) に残す。GitHub Actionsの実行結果は当該コミットの履歴から確認できる。

ローカルテスト・GitHub Actionsの成功をオンラインACとして報告しない。必要な検証が未完了・失敗の場合は、その内容を明示して開発完了と扱わない。過去のAC報告や採用条件は当時の履歴として保持し、現在の完了条件には適用しない。

## 14. 保存と原本

ソースコード、規約、命名・APIカタログ、手順、テンプレート、スニペット、テスト、作業・検証記録の唯一の正式な保存先はGitHubの [`primesosu91/algorithm`](https://github.com/primesosu91/algorithm) の `main` とする。

ChatGPT LibraryやProjectへの常設ファイルは必要ない。作業時に必要な内容をGitHubから取得する。以前の添付・チャット履歴と最新実装に差異がある場合は、最新実装を正とする。取得できない情報を記憶で補わず、未確認事項を明示する。

`UnionFind.cpp` は代表的な設計・記述スタイルの基準であり、設計前にGitHubの確認版を読む。

READMEはカテゴリ別の目次として使い、規約・APIの本文を重複掲載しない。変更理由と検証結果は `records/DevelopmentLog.md` にまとめ、採用状態の別ファイルは作らない。

## 15. バージョン管理

- バージョン履歴はGit/GitHubのコミット履歴で管理する。
- ライブラリコード自体に `v1.0`、`v1.1` などの独自バージョン番号は付けない。
- 変更履歴を確認する必要がある場合はGitの履歴を利用する。

## 16. 既存ライブラリとの統一

新しいライブラリを作成・既存ライブラリを修正するとき、設計前にGitHubの `Rule/NamingAndAPI.md`、最新の `data_structure/UnionFind.cpp`、対象と関連する既存ソースコードを確認し、それらとの統一性を確認する。カタログだけで実装の確認を代替しない。

特に以下を確認する。

- 命名
- API設計
- コメント形式
- 型の使い方
- 添字
- 区間表現
- 初期化方法
- コーディングスタイル

ただし、既存ライブラリに問題がある場合は無条件に踏襲せず、その問題を明示して改善案を提示する。

新規ライブラリの完成後、および既存の公開API・前提条件・返り値の意味が変わった後は、`Rule/NamingAndAPI.md` の一覧、該当API、例外、確認したソースのblob SHAを更新する。原則としてソースとカタログを同じコミットで同期する。コメント・空白だけの変更でも、内容を照合して確認SHAを更新する。

既存APIの破壊的変更には第10節の説明とユーザーの明示的な了承が必要である。カタログ整備だけを理由に既存コード・公開APIを変更しない。

## 17. 管理資料と運用手順

- 規約の正式版は本書、[運用ガイド](CompetitiveProgrammingGuide.md)、[DebugRules](DebugRules.md)。すべて `Rule/` で管理する。
- 命名・API参照は [NamingAndAPI.md](NamingAndAPI.md) と対象・関連ソースを使う。ソースとの不一致は実装を読んでカタログを修正する。
- 日常の作業順と依頼例は [LibraryWorkflow.md](LibraryWorkflow.md)、スニペット仕様は [SnippetRules.md](SnippetRules.md) を参照する。
- AIの入口は [AGENTS.md](../AGENTS.md)。Projectに置く固定指示は [ProjectInstructions.md](ProjectInstructions.md) にまとめる。
- 既存資料の削除・移動は対象を確認し、明示的な依頼の範囲で行う。今回の `docs/` 廃止と `Rule/` への再構成はユーザーが了承した移行である。Gitの履歴は維持する。

## 18. 設計承認と自動処理

新規作成も既存ソースの修正も、次の順序を基本とする。

1. ユーザーが必要なライブラリ・機能・修正内容を伝える。
2. AIが最新mainのコミットを確認し、その版の規約、カタログ、UnionFind、対象・関連ソースを実際に読む。
3. AIが公開型・関数の完全なシグネチャ、意味、引数、返り値、前提、計算量、既存設計との対応を提示する。修正なら変更箇所・既存APIへの影響も示す。
4. ユーザーがその案を明示的に承認する。新規作成・ソース変更は、この承認前に実装・GitHub反映しない。原因調査、反例の再現、設計案の作成は進めてよい。
5. 承認後、AIが実装、C++23での必要な検証、カタログ・スニペット・記録更新、コミット、GitHubへの反映まで行う。通常のGit操作について再度の承認を求めず、ユーザーにコマンド入力を求めない。
6. 完了時にコミットとスニペットのURL、変更内容、使い方・最小例・計算量、検証結果、未確認事項と残る作業を報告する。

承認した仕様や変更範囲を変える必要が生じた場合は、新しい案を説明して了承を得る。破壊的変更の説明・明示的承認は第10節の要件を満たす形で設計承認に含める。

ユーザーが具体的な変更を了承し、案の提示と承認を省略するよう明示した場合、または今回の環境整備のように既存ソースの必要な修正まで一括して許可した場合は、その範囲内で再度の承認を求めない。通常運用では必ず設計案の承認を経る。

作業・検証記録の更新や承認済み環境の保守は、公開API案を再承認する対象ではない。未指定で結果を左右する条件は、必要な情報だけ確認する。

## 19. スニペットの同期

- [templates/AtCoder.cpp](../templates/AtCoder.cpp) を先頭の `!atcoder` とし、`solve()` の最初の行へカーソルを置く。
- 各ライブラリは、先頭の `#include <bits/stdc++.h>` と `using namespace std;` の2行だけを除いた全文を使う。
- 残る改行・空行・コメント・インデントを維持する。スニペットのエスケープ後も、展開される文字列が元の全文と一致するよう確認する。
- 名前はファイル名から拡張子を除いたもの、prefixは `!` と名前の連結。各項目には `prefix` と `body` だけを置く。
- スニペットはソースから生成し、ソース・カタログ・必要なテストと原則同じコミットへまとめる。詳細は [SnippetRules.md](SnippetRules.md)。
