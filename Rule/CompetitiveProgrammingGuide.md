# Competitive Programming 運用ガイド

## 1. 正式な保存先

新規ライブラリ・既存ライブラリの修正・規約改訂・環境整備とGitHub更新は、Competitive Programming ProjectのWorkで行う。ソース、規約、カタログ、手順、テンプレート、スニペット、テスト、作業・検証記録の正式版は [primesosu91/algorithm](https://github.com/primesosu91/algorithm) のmainとする。

ChatGPT LibraryやProjectにファイルを常設する必要はない。Projectの指示には共通ルールとGitHubの入口を置き、毎回AIが最新版を読む。チャット履歴は設計理由や会話の記録であり、最新仕様の原本として使わない。

| 保存場所 | 内容 |
| --- | --- |
| 各アルゴリズムのカテゴリ | AIが分類・フォルダ作成・配置。原則1ライブラリ1 `.cpp`、テスト用mainは含めない |
| `Rule/` | 3規約、命名・APIカタログ、作業手順、スニペット規約、Project指示 |
| `templates/AtCoder.cpp` | ユーザー指定の競プロテンプレート |
| `snippets/competitive_programming.code-snippets` | テンプレートを先頭に置いた全ライブラリのスニペット |
| `tests/` | 本体と同じカテゴリ・相対構成の独立した回帰テスト |
| `tools/` | スニペット生成、カタログ・リポジトリ確認 |
| `records/DevelopmentLog.md` | 変更理由、対象ソース版、検証内容・結果、未確認事項 |
| `AGENTS.md` | AIが最初に読む作業指示 |
| `README.md` | ライブラリと管理資料への目次 |

版はGitのコミット履歴で管理し、ライブラリ本体に独自のv1.0等は付けない。

ライブラリの分類は [RepositoryLayout.md](RepositoryLayout.md) に従う。木を前提とするグラフアルゴリズムは `tree/`、一般のグラフは `graph/`。SegmentTree等は `data_structure/`。新規作成時にユーザーが配置先を指定する必要はなく、必要なフォルダの作成もAIが行う。

## 2. 一度だけ行う設定

[ProjectInstructions.md](ProjectInstructions.md) の全文をProjectの「指示」へ貼り替える。GitHubへ保存しただけでは、この設定欄は更新されない。AIが直接操作できない場合、ユーザーがこの一度の貼り替えを行う。

GitHub編集とコード実行が利用できるWorkチャットを使う。接続・権限が使えなければ、AIはできた作業と未完了の作業を明示する。

スニペットを手元のVS Codeで使う場合の取り込み方は [SnippetRules.md](SnippetRules.md) を参照する。GitHubでの生成・更新と、手元のVS Codeへの取り込みは別の操作である。

## 3. 新規ライブラリと修正

1. ユーザーは必要なライブラリ・機能、または修正内容を伝える。
2. AIは最新mainの確認コミットを特定し、その版の規約、カタログ、UnionFind、対象・関連実装を読む。開始時に確認コミット・参照ファイル・作業範囲を示す。
3. AIは公開型・関数名、引数・返り値、前提、計算量、既存設計との対応と、ソース・テストの予定パスと分類理由を示す。修正では元APIへの影響も説明する。
4. ユーザーが案を承認する。通常運用ではこの承認後にソースを実装・変更する。
5. AIがフォルダ作成・配置、実装、C++23検証、スニペット生成、カタログ・目次・記録更新、コミット、GitHub反映まで進める。通常の配置・Git操作や途中の各工程について繰り返しの承認を求めない。
6. AIが変更内容、使い方、検証結果と未確認事項、コミットとスニペットのURLを報告する。

重要な未指定条件だけ確認する。承認した仕様を変える必要が生じた場合は、新しい案の了承を得る。既存APIの破壊的変更には理由・対象・移行方法を示した具体的な承認が必要。

ユーザーが具体的な環境整備・修正・規約改訂を一括して許可した場合は、指定された範囲の作業に同じ承認を求め直さない。通常の新規作成・ソース変更は上記の手順で行う。

## 4. 不具合修正とデバッグ

[DebugRules.md](DebugRules.md) を適用する。原因・必要な反例を先に調査し、元の設計・名前・コメント・構造を保って必要最小限を修正する。問題文・制約・入力・期待結果・実際の結果を確認できる範囲で使い、原因が未確定なら断定しない。

1問題につき原則1チャットとし、問題文・制約・現在のコード・WA/TLE/RE/CE等を可能な限り提示する。AtCoderのURLだけから未取得の問題内容を補完しない。

## 5. 検証と完了条件

オンライン提出・AC・再ACは開発の必須工程に含めず、「検証中／正式採用」の個別管理は行わない。完了条件は [開発規約](LibraryDevelopmentRules.md) 第13節に従う。

必要な基本・境界・対象固有の検証、適切なランダム・愚直比較と共通チェックを通過させ、ソース・スニペット・カタログ・テスト・管理資料を同期してGitHubへ反映する。動作へ影響する変更後は必要な回帰テストと再検証を行う。

AIは対象版、テストの内容・入力範囲・結果、未確認事項を [DevelopmentLog.md](../records/DevelopmentLog.md) に記録する。GitHub Actionsの当該コミットの結果も取得できれば確認し、実行中・失敗・取得不能は明示する。必要な検証の未完了や失敗を開発完了と扱わず、未実施のオンラインACを確認済みと報告しない。

## 6. チャットの使い分け

新規作成・修正・規約改訂などの新しい依頼は、原則として新しいWorkチャットで始める。関連する以前の履歴のチャットが残っていれば、そのチャットをWorkで継続してもよい。履歴の有無で対応可能な作業を変えず、毎回最新mainから開始する。

| 作業 | Workチャットの例 |
| --- | --- |
| 新しいライブラリ | 新規: 「FenwickTree 作成」 |
| 既存ライブラリの修正 | 新規: 「LCA 修正」。関連する既存Workチャットでも可 |
| 新しい問題のデバッグ | 新規: 問題名・不具合名 |
| 運用方法・設計方針の相談、環境整備 | 新規: 「ライブラリ運用の変更」。関連する既存Workチャットでも可 |
| 規約の作成・改訂 | 新規: 「規約改訂」。関連する既存Workチャットでも可 |

毎回長い起動文や全ソースを貼る必要はない。要望と必要な条件を伝え、規約・実装の確認はAIが行う。通常チャットで相談を始めた場合も、GitHubを変更する作業はWorkへ引き継ぐ。以前のチャットをWorkで継続できない場合は、新しいWorkチャットを使う。

AIは新しいチャットでも最新mainのAGENTS・Rule・対象ソース・テスト・DevelopmentLogを実際に読み、開始時に確認コミット・参照資料・今回の範囲を示す。過去チャットの本文、添付ファイル、会話の記憶を開始の必須条件にしない。

途中で新しいWorkへ移る場合は、AIが確認コミット・対象パス・今回の要望・確認できた設計と承認範囲・作業版の保存先・未完了事項を引き継ぎ文にまとめる。取得できない仕様・承認・未保存差分を復元済みと扱わない。

## 7. 規約改訂と資料の整理

実際の不足や問題に応じて、GitHubの現行規約を確認して必要箇所だけ改訂する。関連するAGENTS・手順・カタログ・チェックとの矛盾を確認し、同じコミットで反映する。Projectの固定指示を変える必要がある場合だけ、新しい全文を提示する。

常設ファイル0個の運用は、ChatGPTの既存ファイル削除を必須としない。Project添付の解除とLibraryファイルそのものの削除は別の操作であり、明示的に依頼された対象のみ保存状況を確認して扱う。今回のGitHubのdocs廃止は許可された移行である。

未確認資料を記憶から復元せず、未完了の更新を完了と報告しない。Gitの履歴や無関係な変更を消さない。
