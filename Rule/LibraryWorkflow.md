# LibraryWorkflow — 依頼と承認からGitHub更新まで

対象は [primesosu91/algorithm](https://github.com/primesosu91/algorithm) のmain。正式版はGitHub。AIは [AGENTS.md](../AGENTS.md) と [Rule一覧](README.md) を入口にする。

## 1. 初回設定

[ProjectInstructions.md](ProjectInstructions.md) の全文をCompetitive Programming Projectの「指示」へ貼り替える。GitHub保存だけではProject設定は変わらない。ファイルの常設アップロードは不要。

GitHub編集とコード実行が利用できるWorkチャットを使う。スニペットをVS Codeへ入れる場合は [SnippetRules.md](SnippetRules.md) 第4節に従う。通常のGitコマンドはAIが担当する。

新規作成・修正・規約改訂・環境整備は原則新しいWorkチャットで開始する。関連する以前の履歴が残っていれば、そのチャットをWorkで継続してもよい。新規チャットでも最新mainの規約・対象ソース・テスト・作業記録から対応する。GitHubの変更はWorkで行う。

## 2. 日常の流れ

| 段階 | ユーザー | AI |
| --- | --- | --- |
| 依頼 | 必要な機能・用途、または修正内容を伝える | 最新mainと規約・既存実装を読む |
| 設計確認 | 型・関数名・引数・返り値・前提を確認する | 計算量と既存設計との対応、ソース・テストの予定パスと分類理由を示す |
| 承認 | 「この案で進めて」と明示する | 承認した範囲で実装へ進む |
| 完了 | 報告を確認する | フォルダ作成・配置、実装・検証・スニペット・カタログ・目次・記録を同期し、コミットしてGitHubへ反映する |

承認後は各工程に「次へ」を繰り返す必要はない。重要な未指定条件や承認した仕様の変更だけ追加確認する。通常のGitHub反映は設計承認に含まれる。

配置先の指定・フォルダ作成・ファイル移動もAIが担当する。分類の基準は [RepositoryLayout.md](RepositoryLayout.md)。ユーザーに配置のための操作を求めない。

オンライン提出・AC・再ACの確認は必須工程に含めない。ユーザーが行う通常の流れは、依頼・設計案の承認・完了報告の確認となる。




設計だけなら「今回はAPI案だけ。実装しないで」と伝える。新規・修正・規約改訂とも原則新しいWorkチャットで依頼し、関連する既存チャットをWorkで継続することもできる。旧チャットや全ソースの貼り付けは必要ない。

## 4. AIの調査と設計

1. mainの最新の完全なコミットSHAを取得する。
2. そのSHAに固定してAGENTS、開発規約、運用ガイド、本書、RepositoryLayout、SnippetRulesを読む。不具合修正はDebugRulesも読む。
3. [NamingAndAPI.md](NamingAndAPI.md) の共通方針と対象項目、[UnionFind.cpp](../data_structure/UnionFind.cpp)、対象・関連実装、保存済みテスト、関連する [DevelopmentLog.md](../records/DevelopmentLog.md) の項目を読む。
4. 確認コミット、参照したファイル、今回の範囲を報告する。カタログとの不一致は最新実装を正として確認する。
5. 型名・完全な関数シグネチャ、意味、引数・返り値、状態変更、前提・呼出し順、添字・区間・未該当値・計算量と、AIが選んだソース・テストの予定パスと分類理由を示す。修正では変更前後のAPIへの影響も示す。
6. 通常は設計承認を待って実装する。破壊的変更は理由・対象・移行方法も承認する。具体的な一括許可が既にあれば同じ確認を繰り返さない。

通常は共通資料と関連する少数のソースを読み、全体点検が必要な場合のみ横断確認する。取得できない内容を会話や記憶で補完しない。

## 5. 承認後の実装と検証

1. RepositoryLayoutに従ってAIが該当カテゴリを選び、必要なフォルダを作成し、原則1ライブラリ1 `.cpp` として実装する。木を前提とするグラフアルゴリズムは `tree/`、一般のグラフは `graph/`、汎用データ構造は `data_structure/`。外部マクロ・型エイリアス・自作テンプレート・ACLに原則依存しない。
2. 不具合修正では原因と反例を確認し、元の名前・構造・コメントを維持して必要最小限を修正する。
3. C++23で対象固有の基本・境界・適切なランダム・愚直比較を行い、本体と同じ相対構成の `tests/カテゴリ/LibraryName.test.cpp` へ保存する。対象includeも本体のパスへ合わせる。入力範囲・seed・未確認事項を残し、計算量・数値範囲も確認する。
4. 公開宣言と本体を読んでカタログを更新し、Git blob SHAをcatalog-sourceへ記録する。SHAだけ更新して調査済みにしない。
5. [generate_snippets.py](../tools/generate_snippets.py) でテンプレートと全ライブラリからスニペットを再生成する。
6. 共通チェックと必要な追加検証を通過させる。
7. 対象ソース版、変更理由、実施したテスト・入力範囲・結果、未確認事項をDevelopmentLogへ記録する。必要ならREADMEも更新する。

AIが実行する共通コマンド:

```bash
python3 tools/generate_snippets.py
python3 tools/check_repository.py
```

必要なメモリ・未定義動作の確認:

```bash
python3 tools/check_repository.py --sanitizers
```

同じツリーで構文確認済みの場合に限り `--skip-syntax` で再確認を省略できる。ユーザーへ通常のコマンド入力を求めない。

| チェック | 確認する内容 |
| --- | --- |
| 配置・カタログ | 本体とテストのパス・include対応、収録、Git blob SHA、管理資料の相対リンク |
| スニペット | 原本との一致、キー・名前・prefix・順序・カーソル |
| C++23 | 全ライブラリ、テンプレート、テンプレートへ各ライブラリを挿入したコードの構文 |
| 動作 | 保存済み回帰テストと必要な対象固有の追加検証 |
| ASan/UBSan | 必要な境界・メモリ・未定義動作の検出 |

構文確認だけでテンプレート型の全組合せや全入力の正当性を認定しない。テストの説明は [tests/README.md](../tests/README.md)。保存済み検証はGitHub Actionsでも実行する。

## 6. カタログと記録

カタログには明示された公開型・関数・コンストラクタ・演算子・friend関数・変数を、テンプレート・既定引数・const・参照まで含めて記録する。通常利用APIとpublicの内部補助を区別する。

引数順・値／参照・前提・初期状態・構築順・合理的な例外も本体から確認する。部分更新で全体を再調査済みにしない。基準コミットとblob SHAで未コミット版を特定し、自分を含む未確定コミットSHAを捏造しない。

[DevelopmentLog.md](../records/DevelopmentLog.md) に日付・基準コミット・対象ソース版・理由・変更・テストの内容と範囲・結果・未確認事項を記す。GitHub Actionsの結果は当該コミットに対応する実行履歴で確認する。採用状態やAC待ちを管理する別ファイルは作らない。

## 7. コミットとGitHub反映

1. 意図した差分と必要な検証結果を確認する。
2. mainのheadを再取得する。変わっていれば最新差分を統合して必要な検証をやり直す。
3. ソース、スニペット、テスト、カタログ、関連記録を原則同じコミットへまとめる。
4. GitHub連携または認証済みGitで非強制更新する。Git Data APIなら基準treeを継承し、親とexpected_shaを最新headへ合わせる。
5. 更新後のheadと差分を取得し、許可された移行以外のファイル消失・無関係な変更がないことを確認する。
6. 当該コミットのActionsを取得できれば確認し、実行中・失敗・取得不能はその状態で報告する。
7. 変更内容、使い方・最小例・計算量、検証結果と未確認事項、コミットとスニペットのリンク、残る作業を報告する。

強制push、履歴削除、未保存・無関係な変更の消去で失敗を解消しない。保護規則でmain直接更新できなければブランチ・PRへ保存し、必須レビュー・チェックを迂回しない。

Workで依頼を受けている間にAIが作業する方式。Actionsは保存済みコード・テストの検証であり、チャット終了後に新機能を自発的に作る常駐AIではない。

## 8. 完了基準と検証結果

[開発規約](LibraryDevelopmentRules.md) 第13節に従い、必要な検証と資料の同期、コミット・GitHub反映まで行う。オンラインACや再AC待ちを理由に完了を保留しない。必要な検証の未完了・失敗、main未反映、Actionsの実行中・失敗・取得不能はそのまま報告する。

動作変更後は必要な回帰テストと変更箇所の再検証を行う。コメント・空白だけの場合もソース・カタログ・スニペットの整合性を確認する。実施した検証の範囲を明示し、ローカル検証・GitHub Actionsの成功をオンラインACとして報告しない。

## 9. 更新失敗時

ローカルの完成作業とGitHub未反映を区別する。取得不能・権限・保護規則・同時更新に応じて対応し、未完了を成功と報告しない。過去資料・未コミットファイル・スニペットを記憶から復元しない。

新しいWorkチャットでも、最新mainの資料を確認して今回の依頼から開始できる。途中作業を引き継ぐ場合は [運用ガイド](CompetitiveProgrammingGuide.md) 第6節に従い、確認コミット・対象・合意済み仕様・確認できた承認範囲・作業版の保存先・未完了事項を示す。
